# 004. Индексация по сгенерированным вопросам, rubert-tiny2 на CPU и порог сходства

## Статус

Принято

## Контекст

Фрагменты базы знаний - это официальный текст («Для получения справки об обучении необходимо
подать заявление в дирекцию…»), а студенты спрашивают разговорно («где взять справку для
военкомата»). Прямое сравнение эмбеддингов вопроса и такого текста работает плохо.

Сервер слабый (1 CPU, ~1 ГБ RAM), платных эмбеддинг-API нет.

## Решение

- При добавлении фрагмента (`NewData`) LLM генерирует несколько вопросов, на которые он
  отвечает; в Chroma индексируются **эмбеддинги этих вопросов**, связанные с id фрагмента
  в PostgreSQL. Поиск идёт «вопрос студента <-> вопросы к фрагменту».
- Модель эмбеддингов - `cointegrated/rubert-tiny2` (sentence-transformers, CPU): маленькая,
  быстрая, хорошо понимает русский. `torch` ставится CPU-колесом, без CUDA.
- Chroma - локальный персистентный клиент (косинусное расстояние), без отдельного сервера.
- Фрагменты с косинусным сходством ниже `SEARCH_SIMILARITY_THRESHOLD` отбрасываются: лучше
  честно сказать «в базе нет», чем подсунуть LLM нерелевантный контекст.
- Тег подразделения (`division`) даёт мягкую приоритизацию: сначала документы с совпавшим
  тегом, затем общий поиск.

## Последствия

- Добавление записи стоит одного вызова LLM; если LLM не сгенерировала вопросов, запись не
  сохраняется (иначе её никогда не найдут).
- Порог сходства нужно калибровать по реальным логам (DEBUG показывает оценки).
- Модель (~120 МБ) кэшируется в volume, чтобы не качать при каждом пересоздании контейнера.
