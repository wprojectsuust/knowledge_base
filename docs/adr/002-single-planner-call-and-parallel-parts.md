# 002. Один вызов LLM-планировщика и параллельные части ответа

## Статус

Принято

## Контекст

Студенты пишут как в мессенджере: «какие завтра пары у ТОП-106Б и где деканат ФИРТ»,
«а туда как пройти?». В одном сообщении бывает несколько разных задач (расписание, поиск по
базе знаний, маршрут), а часть смысла живёт в предыдущих репликах.

Первая версия классифицировала вопрос несколькими отдельными вызовами LLM (сначала «это
расписание?», потом «какая группа?», потом «какая дата?»). Это было медленно (каждый вызов -
секунды), дорого по лимитам бесплатных API и всё равно не умело «два вопроса в одном».

## Решение

- `PlanQuestion` делает **один** вызов LLM и возвращает JSON-план `QuestionPlan` с ключами
  `search`, `schedule`, `route`, `clarify` - любые из них могут быть заполнены одновременно.
- В том же вызове LLM переформулирует части с учётом истории чата («туда» -> конкретное место)
  и нормализует данные (группа в формате ИСУ, относительные даты -> абсолютные).
- `Question` выполняет части через `asyncio.gather` - параллельно.
- Если частей больше одной, `ComposeAnswer` сводит их в один связный ответ на исходный вопрос;
  шаблонный текст маршрута вставляется как есть, без пересказа.
- Невалидный JSON от LLM не роняет запрос - план откатывается к обычному поиску по исходному тексту.

## Последствия

- На типичный вопрос - 2 вызова LLM (план + ответ), на составной - 3-4, а не 5-7.
- Промпт планировщика - самое хрупкое место: правила («маршрут только если прямо спросили,
  как пройти») приходится держать в нём явно и покрывать тестами на разбор JSON.
- Кэш вопрос-ответ используется только для чистого поиска без истории: расписание зависит от
  даты, маршрут считается мгновенно, а с историей один и тот же текст значит разное.
